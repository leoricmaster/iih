# IIH 信息架构

> 消费方侧的接触点、动线与页面：用户旅程定接触点与反馈时机，信息架构把接触点组织为页面与导航。单消费方前提（立项 §7）；对象与状态以领域模型为准，术语以术语表为准；推送通道与快捷反馈口径已裁决（§4/§5，decision-11）。

## 1. 消费方与节奏

单消费方（用户本人）跨两条动线：

- **消费动线**（高频 · 被动）：读分发情报、给类型化反馈——原则是反馈发生在消费现场，零跳转；
- **管理动线**（低频 · 主动）：声明 / 调整情报需求、登记探究任务、人工录入、确认新信源。

节奏三类：**日常批量**（晨间分发汇总）、**事件即时**（翻案警报、录入后回看）、**项目式**（任务探究期间工作台停留）。

## 2. 用户旅程

四条核心场景（立项 §1）落地为旅程；**粗体**为反馈动作——进化支柱的入口，全部落在消费现场或详情页一步内。

### 2.1 订阅监控（日常 · 高频）

订阅「长期跟踪 W 公司」激活后，系统自动盯信源。晨间，推送通道送达昨日新核实条目的卡片（陈述摘要 + 二维评级 + 独立信源计数 + 链接）。用户在消息内快扫：多数一键**有效**；不相关 / 过期的顺手标记；个别点开详情看转引链穿透与评级依据，必要时**评级异议**。周频在需求页按分发记录的送达 / 反馈覆盖微调内容规格。出口：条目收到反馈，或保持送达待处理。

### 2.2 人工录入（事件驱动）

参会 / 访谈结束，用户打开录入页：选媒介，上传载体素材（录音 / 照片 / 笔记），可关联情报需求。素材与自动采集走同一条流水线（线索 → 审查 → 核实评级），进度在条目列表按人工提交过滤可见。核实完成后经正常分发回来——用户对自己提交的内容最知真假，**有效**与**事实错误**在这里价值最高。

### 2.3 任务探究（项目式 · 主动）

出现具体疑问（「露天矿装车市场空间有多大？」——无研报直接回答，需多方法测算出区间，参数大部分在互联网）。用户登记**探究任务**（问题陈述 + 可选**附件**：自由文本，如指标清单、测算框架、信源指引；转写首个区间命题为可选——估算类可不转写）。定向智能体按附件将探究任务**递归分解为子任务**（各测算法，可带子附件）+ 叶子情报需求，逐项盯参数（v1 用户手动落成，之后系统无人值守，decision-15；附件留空则智能体自行发挥）。用户在工作台（探究任务详情）停留：任务树、命中条目聚合可见。叶子参数齐时各子任务**构造性测算由用户完成**出子命题（判定者记人，置信度仍由公式从账本变量计算，decision-15），父任务取子命题按框架合成**作答**（登记即判定）落成结论命题，可被引用；对结论命题提**事实错误**触发重估。出口：区间结论命题被引用（间接消费），探究任务结题，子需求与子任务关闭（命题不受结题影响，可继续被引用与翻案）。

### 2.4 复核与翻案（中断驱动 · 被动）

系统侧变化——条目作废级联重估、结论进入重估中、存疑复核期到、评级重评完成——经推送通道送**警报**（与日常分发区分级别）。用户点开看变化前后对比（评级版本、置信度变化）与推理记录依据。多数情形无需操作（重估自动收敛）；对触发源条目可反馈**事实错误** / **评级异议**。出口：结论维持 / 修订 / 推翻，全程版本化。

### 2.5 触点汇总

| 接触点 | 承载 | 节奏 |
|---|---|---|
| 推送通道 | 分发卡片（可反馈）、翻案警报、新信源确认提醒 | 晨间批量 + 事件即时 |
| Web · 收件箱 | 待反馈条目、警报汇总、新信源确认队列（decision-09） | 每日 |
| Web · 对象页 | 条目 / 探究任务 / 命题 / 需求 / 信源库的检索与管理 | 按需 |
| Web · 录入页 | 人工提交 | 事件后 |
| Web · 账户区 | 单账号信息、推送通道绑定、分发偏好 | 低频 |

## 3. 页面与导航

「薄」的定义：**对象一页制**——每个一等对象一个列表页 + 一个详情页（唯一复合页是收件箱，聚合三类待办）；不设独立仪表盘，需求覆盖度量内联在需求页；反馈不设独立页，记录内联在条目详情与命题详情；运维不进 UI（CLI / 日志，技术架构 §7）。

导航：收件箱为首页，主导航五个对象页（桌面左侧栏，移动端折为顶栏），人工录入为全局动作按钮、不占导航位；右上角账户区承载单账号信息、推送通道绑定与分发偏好（推送通道的配置归宿；v1 最小，多消费方场景立项 §7 不做）。

| 页面 | English | 对象（默认视图） | 核心动作 |
|---|---|---|---|
| 收件箱 | Inbox | 情报条目（已送达待反馈）+ 警报 + 待确认信源 | 读、反馈、确认信源 |
| 情报条目 | Intelligence Item | 条目（已核实起，全状态可滤） | 检索、读转引链与独立信源计数、反馈（六类型） |
| 探究任务 | Inquiry Task | 探究任务（按状态分组） | 登记问题、挂附件、递归分解子任务、催生子需求、工作台聚合（任务树 / 命中条目） |
| 命题 | Claim | 命题（按状态分组：假设/结论/已证伪；结论一览由此筛） | 登记断言、候选命题判定与结论反馈、推理记录、催生求证需求 |
| 情报需求 | Intelligence Requirement | 需求（订阅 / 任务） | 建需求、调内容规格、暂停 / 关闭、看覆盖度量 |
| 信源库 | Source Registry | 信源 + 信源画像 | 看信用档与画像、确认新信源 |
| 人工录入 | Manual Submission | 素材 → 线索 | 选媒介、上传载体、看管线进度 |

条目详情页是消费动线与核查动线的交汇点：陈述、二维评级及历史版本、转引链穿透视图、独立信源计数、出处信源、事件时间、反馈记录，一屏尽出。命题详情页是求证线的交汇点：陈述、状态、置信度、推理记录、引用证据（情报条目 / 子命题）、结论反馈，一屏尽出。

## 4. 反馈入口

六类型（领域模型 §6）开放于三个入口，原则：**反馈挂在被评价对象上，一步可达**。

| 入口 | 开放类型 | 说明 |
|---|---|---|
| 条目 · 推送卡片 | 全六类型一键；事实错误跳详情补理由 | 反馈在消费现场 |
| 条目 · Web 列表 / 详情 | 全六类型，理由可补写（事实错误必填） | 理由供学习通路使用 |
| 命题 · 详情（结论态） | 事实错误（触发重估中） | 结论反馈仅作用于结论态命题；非结论态不设入口，翻案由系统触发 |

快捷反馈口径已裁决（decision-11）：一键反馈以「快捷 · {类型}」为默认理由，Web 内可补写；事实错误理由必填。

## 5. 推送通道（decision-11）

旅程对通道的四点硬要求：

1. **主动触达**：翻案警报不能等用户来访（痛点「不可翻案」的对策）；
2. **批量摘要**：晨间分发是批量节奏，非逐条轰炸；
3. **消息内反馈**：反馈应发生在送达现场（分发记录以反馈闭环，领域模型 §4.1），多一跳覆盖率掉一截；
4. **卡片结构化**：陈述摘要 + 二维评级 + 独立信源计数 + 链接，一眼可判。

| 选项 | 主动触达 | 消息内反馈 | 批量摘要 | 评价 |
|---|---|---|---|---|
| 站内 | ✗ 需主动来访 | ✓ | ✓ | 独立不可用，仅作兜底与存档 |
| 邮件 | ✓ | 弱：回信解析不可靠，实际仍跳 Web | ✓ | 可行，但反馈多一跳 |
| IM 机器人 | ✓ | ✓ 消息内按钮 | ✓ | 满足全部要求 |

**已裁决（decision-11）**：IM 机器人为唯一推送通道，站内收件箱兜底，邮件 v1 不做；产品 = 用户日常最高频的 IM（微信个人号出局），实现须满足消息内交互且不引入公网暴露的新组件（技术架构 §1）。

## 6. 范围边界

- 移动端仅保证消费动线（收件箱、条目详情、反馈）响应式可用，管理页桌面优先；
- 多消费方分发、权限、订阅门户不在 v1（立项 §7）；
- 页面视觉与交互稿不属本文，实现前另出。
