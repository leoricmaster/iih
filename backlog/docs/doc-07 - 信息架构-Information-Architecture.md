# IIH 信息架构

> 消费方侧的接触点、动线与页面：用户旅程定接触点与反馈时机，信息架构把接触点组织为页面与导航。单消费方前提（立项 §7）；对象与状态以领域模型为准，术语以术语表为准。

## 1. 消费方与节奏

单消费方（用户本人）跨三条动线：

- **消费动线**（被动 · 高频）：读分发情报、给类型化反馈——基础用法，反馈发生在消费现场、零跳转；
- **探究动线**（主动 · 项目式）：登记研究课题、工作台与图谱跟进、构造性测算、对结论提事实错误——核心工作模式，关注导向、随功能完善趋于相对高频；
- **管理动线**（主动 · 事务 · 低频）：声明 / 调整情报需求、人工录入、确认新信源。

节奏三类：**日常批量**（晨间分发汇总）、**事件即时**（翻案警报、录入后回看）、**项目式**（研究课题探究期间工作台停留）。

## 2. 用户旅程

四条核心场景（立项 §1）落地为旅程；**粗体**为反馈动作——进化支柱的入口，全部落在消费现场或详情页一步内。

### 2.1 冷启动（首次启用 · 一次性）

新系统信源库为空，定向智能体无途径可派采集任务（依赖信源与途径画像选途径，doc-06 §2），需用户先喂种子。用户在信源库登记若干种子信源及其互联网途径（如 W 公司 · 官网与公众号，新华社 · 官网——主体一登记、途径随手添），随后声明首个情报需求并激活——定向智能体才有途径产出采集任务。登记只收互联网途径（系统自动拉取）；线下场景不经登记——素材由人工录入，信源与途径由采集智能体从素材识别归因，新信源经确认入信源库（decision-05）。采集执行时的池外自由探索（decision-05）发现关联信源，经确认后滚雪球扩大信源池。种子只需极少量（每个需求一两处源头），后续信源增长主要靠系统发现、用户确认。出口：需求激活、采集启动，进入常驻监控。

### 2.2 常驻监控（日常 · 高频）

常驻需求「长期跟踪 W 公司」激活后，系统自动盯信源。晨间，推送通道送达昨日新核实条目的卡片（陈述摘要 + 二维评级 + 独立信源计数 + 链接）。用户在消息内快扫：多数一键**有效**；不相关 / 过期的顺手标记；个别点开详情看转引链穿透与评级依据，必要时**评级异议**。定期在需求页按分发记录的送达 / 反馈覆盖微调内容规格。出口：条目收到反馈，或保持送达待处理。

### 2.3 人工录入（事件驱动）

参会 / 访谈结束，用户打开录入页：选媒介，上传多个附件（拖拽，系统自动识别载体）；或直接写文字纪要。素材与自动采集走同一条流水线（线索 → 审查 → 核实评级），相关性由审查按激活情报需求自动匹配；进度在条目列表按人工提交过滤可见。核实完成后经正常分发回来——用户对自己提交的内容最知真假，**有效**与**事实错误**在这里价值最高。

### 2.4 研究课题探究（项目式 · 主动）

出现具体疑问（「露天矿装车市场空间有多大？」——无研报直接回答，需多方法测算出区间，参数大部分在互联网），用户要的是**答案**而非情报流。

1. **登记**：登记研究课题（问题陈述 + 可选提示词：指标清单、测算框架、信源指引等自由文本，留空则智能体自行发挥）。已有候选答案或场景草稿，登记后在工作台补记（候选答案 = 假设命题，由证据持续检验）。
2. **工作台跟进**：定向智能体按提示词递归分解为子课题与情报需求（decision-06）；用户在研究课题详情停留——课题树、命中条目聚合可见。
3. **测算出子命题**：叶子输入齐时，各子课题的构造性测算由用户完成、出子命题（判定者记人，置信度由公式从账本变量计算，decision-06）。
4. **合成作答并结题**：父课题取子命题按框架合成答案命题（登记即判定），落成结论命题、可被引用；对结论命题提**事实错误**触发重估。区间结论命题被引用（间接消费）后研究课题结题，子需求与子课题关闭；命题不受结题影响，可继续被引用与翻案。

### 2.5 复核与翻案（中断驱动 · 被动）

系统侧变化——条目作废级联重估、结论进入重估中、存疑复核期到、评级重评完成——经推送通道送**警报**（与日常分发区分级别）。用户点开看变化前后对比（评级版本、置信度变化）与推理记录依据。多数情形无需操作（重估自动收敛）；对触发源条目可反馈**事实错误** / **评级异议**。出口：结论维持 / 修订 / 推翻，全程版本化。

## 3. 页面与导航

「薄」的定义：**对象一页制**——每个核心对象一个列表页 + 一个详情页；跨对象视图两个：收件箱聚合三类待办，图谱承载实体（不设独立实体列表 / 详情页，节点点选面板即实体详情）；不设独立仪表盘，需求覆盖度量内联在需求页；反馈不设独立页，记录内联在条目详情与命题详情；运维不进 UI（CLI / 日志，技术架构 §7）。

导航：收件箱为首页，主导航五个对象页 + 图谱页按 §1 三条动线分组陈列（消费：收件箱、情报条目；探究：研究课题、命题、图谱；管理：情报需求、信源库），桌面左侧栏、移动端折为顶栏；人工录入为全局动作按钮、不占导航位；右上角账户区（低频）承载单账号信息、推送通道绑定与分发偏好（推送通道的配置归宿；多消费方场景立项 §7 不做）。

| 页面 | English | 对象（默认视图） | 核心动作 | 节奏 |
|---|---|---|---|---|
| 收件箱 | Inbox | 情报条目（已送达待反馈）+ 警报 + 待确认信源（decision-05） | 读、反馈、确认信源 | 每日 |
| 情报条目 | Intelligence Item | 条目（已核实起，全状态可滤） | 检索、读转引链与独立信源计数、反馈（六类型） | 按需 |
| 研究课题 | Research Question | 研究课题（按状态分组） | 登记问题、挂提示词、递归分解子课题、催生子需求、工作台聚合（课题树 / 命中条目） | 项目式 |
| 命题 | Claim | 命题（按状态分组：假设/结论/已证伪；结论一览由此筛） | 登记断言、答案命题判定与结论反馈、推理记录、催生需求盯证据 | 按需 |
| 图谱 | Knowledge Graph | 实体（点选看提及清单 / 别名 / 归并历史）；关系边为派生投影（点边看共现的条目 / 命题；边加权与过滤为实现要点）；断连孤岛标注 | 浏览、点入条目 / 命题 / 课题、孤岛提示（声明新情报需求） | 按需 / 项目式 |
| 情报需求 | Intelligence Requirement | 需求（按状态分组） | 建需求、调内容规格、暂停 / 关闭、看覆盖度量 | 按需 |
| 信源库 | Source Registry | 信源 + 途径 | 登记种子信源与互联网途径（线下途径经人工录入归因补记）、看信用档与画像（主体 / 途径两栏）、确认新信源 | 按需 |
| 人工录入 | Manual Submission | 素材 → 线索 | 选媒介、上传附件、看流水线进度 | 事件后 |

条目详情页是消费动线与核查动线的交汇点：摘要优先（陈述、二维评级、状态、独立信源计数、出处信源、事件时间、反馈快捷常驻、状态自适应主区），核查深区（转引链穿透、评级历史、关联图、元数据、反馈记录）按需展开、带摘要折叠。命题详情页是求证线的交汇点：陈述、状态、置信度、推理记录、引用证据（情报条目 / 子命题）、结论反馈，一屏尽出。两页与研究课题工作台均含局部关联图（实体提及 + 派生共现，点入图谱页）。

## 4. 推送通道

旅程对通道的四点硬要求：

1. **主动触达**：翻案警报不能等用户来访（痛点「不可翻案」的对策）；
2. **批量摘要**：晨间分发是批量节奏，非逐条轰炸；
3. **消息内反馈**：反馈应发生在送达现场（分发记录以反馈闭环，领域模型 §4.3），多一跳覆盖率掉一截；
4. **卡片结构化**：陈述摘要 + 二维评级 + 独立信源计数 + 链接，一眼可判。

已裁决：IM 机器人为唯一推送通道（满足全部四点），站内收件箱兜底，邮件不做；产品 = 用户日常最高频的 IM（微信个人号出局），实现须满足消息内交互且不引入公网暴露的新组件（技术架构 §1）。

## 5. 反馈入口

六类型（领域模型 §6）开放于三个入口，原则：**反馈挂在被评价对象上，一步可达**。

| 入口 | 开放类型 | 说明 |
|---|---|---|
| 条目 · 推送卡片 | 全六类型一键；事实错误点选后跳详情补理由（必填） | 反馈在消费现场 |
| 条目 · Web 列表 / 详情 | 全六类型，理由可补写（事实错误必填） | 理由供学习通路使用 |
| 命题 · 详情（结论态） | 事实错误（触发重估中） | 结论反馈仅作用于结论态命题；非结论态不设入口，翻案由系统触发 |

快捷反馈口径：一键反馈以「快捷 · {类型}」为默认理由，Web 内可补写；事实错误理由必填。

## 6. 范围边界

- 移动端仅保证消费动线（收件箱、条目详情、反馈）响应式可用，管理页桌面优先；
- 多消费方分发、权限、订阅门户不在范围（立项 §7）；
- 页面视觉与交互稿不属本文，实现前另出。
